# 审计注释、边角料与分层

用在**功能已经跑通之后**。功能没通就先去把功能弄通 —— 对着不工作的代码
做审计是浪费。

## 前提

项目根需有 `.comment-standard.json`。没有则该项目未启用——
**先问用户要不要启用，不要自作主张创建。**

这个文件里的每一项都是用户的声明，不是你的判断：

| 键 | 声明的是 | 影响 |
|---|---|---|
| `layers` | 哪些目录构成依赖层，由核心到外围 | 不写则 R2 跳过；D1 只要声明了 `vendored` 也会跑 |
| `vendored` | 哪些目录是复制进来的第三方代码 | 不写则那些代码会被当自己的审 |
| `output_roots` | 实验输出区的目录名，列表 | 默认 `["runs"]` |
| `codegraph` | 索引范围的加减 | 见下节 |

`output_roots` 一律写成列表，只有一个也是：

    "output_roots": ["runs"]
    "output_roots": ["runs", "outputs", "logs"]

真实项目常同时有几个输出目录，换过根的（`runs` → `runs-v2`）两个也都还在。

最小配置是 `{}`。这时 R0/R1/R3/R4/R5/R6/C1 照常跑，只有依赖层级相关的
R2、D1 跳过；默认输出区 `runs/` 存在的话 D2 也会跑。

**你不改这个文件。** 审计时发现该声明而没声明的，在汇报里说明理由和建议写法，
由用户决定。两种最常见的：

- 项目明显有分层结构（核心包、脚本目录、临时脚本），但没写 `layers`——
  建议写上，能启用 R2 和 D1
- 有复制进来的官方代码（如 `sd15/`），但没写 `vendored`——那些函数会被大量
  报 R0，而它们本来就不该按我们的标准写注释

## 怎么判断 layers 该怎么写

用户第一次启用时多半不知道填什么。**先看目录结构再给具体建议，
不要甩一句格式让他自己填。**

    ls <项目根>
    codegraph query <某个核心符号>      有索引的话看看谁依赖谁

判据只有一条:**谁离不开谁**。

- **最内层**是拿掉它别的就跑不了的那个 —— 通常是同名于项目的包
  (`ovam/`、`src/<项目名>/`),或者放模型、算法主体的目录
- **最外层**是拿掉它主体照常跑的 —— 临时脚本、探针、`temp_scripts/`、`sandbox/`
- **中间层**是调用核心、又被外层调用的 —— 评测、训练、`scripts/`、`tools/`

判不准就问一句:「拿掉 `scripts/`,`ovam/` 还能用吗?反过来呢?」
答案通常一秒就出来。

### 常见形态

| 项目长这样 | 建议 |
|---|---|
| `ovam/` + `scripts/` + `temp_scripts/` | `["ovam", "scripts", "temp_scripts"]` |
| 只有一个包 + 根上几个脚本 | `["<包名>"]` —— 根上的脚本不分层,自动跳过校验 |
| 全平铺,没有目录结构 | **别写 `layers`**。分层是描述现状,不是强加结构 |
| 分不清中间层 | 先写两层 `["核心", "外围"]`,跑一轮看 D1 报什么再细分 |

**层不必覆盖所有目录。** 没进任何层的路径跳过层级校验 —— 那是「没说」,
不是「错了」。宁可少写一层,也不要为了凑齐而硬塞。

**顺序错了比不写更糟。** 写反了会把正常的依赖全报成违规,用户第一次跑就
看到满屏 D1,多半直接把配置删了。拿不准顺序就先只写最内层那一个。

## 索引范围：你只看，不改

索引哪些目录是用户的决定，写在 `.comment-standard.json` 的 `codegraph` 键里。
**不要自己去改它**，也不要因为觉得某个目录没必要索引就动手加 `exclude`。

你能做的是观察并报告。建完索引看一眼实际收了什么：

    sqlite3 <项目根>/.codegraph/codegraph.db "SELECT path FROM files;"

发现明显不该在里面的东西——复制进来的整个权重仓库、几万行的 notebook 导出、
建索引明显变慢——**在汇报里说一句**：哪个目录、多少文件、建议排除。
让用户决定改不改。

多索引一点通常无害：`explore` 和 `callers` 还能找到那些文件。
但注意它们**会**参与注释规则和 R1——只有层级规则（R2/D1）要求文件属于
某个已声明的层。所以多出来的目录会带来多余的 R0 告警，这也是值得报告的信号。

### 用户问起时的事实

**`include` 不是白名单。** 这是最容易误解的一点：两个键都是在默认结果上做加减，
没有「只索引这几个」的模式。

| 键 | 作用 |
|---|---|
| `exclude` | 从默认结果里**减掉**（能减掉已被 git 跟踪的目录，`.gitignore` 做不到） |
| `include` | 往默认结果里**加回**（把被 `.gitignore` 丢掉的源码拉回来） |
| `deprioritize` | 仍然索引，但在搜索里不抢排名 |
| `extensions` | 映射自定义后缀 |

实测：五个目录的项目里写 `"include": ["ovam","scripts","temp_scripts"]`，
结果仍是 `Indexed 5 files`；换成 `"exclude": ["notebooks/","legacy/"]`
才变成 3 个。

`deprioritize` 适合 `temp_scripts/` 这种符号名和正式代码撞车的目录。

配置写在 `.comment-standard.json` 里，刷新时写出 `codegraph.json`，**一处维护**。
它是派生文件，每次刷新覆盖，手改留不住。

删掉配置里的 `codegraph` 段**不会**删除已生成的 `codegraph.json`——分不清它是
我们生成的还是用户自己写的，删掉是毁数据。这时命令会提示它还在、不再受管理。
看到这条提示就在汇报里带一句，让用户决定要不要删。

## 运行

    python3 ../../scripts/refresh.py <项目根> --json

`scripts/refresh.py` 在插件根下，路径**相对本技能目录**。调用本技能时
你已经被告知它的**基准目录**，把这个相对路径接在基准目录后面写成绝对路径再跑，
不要靠当前工作目录去拼。

这一条命令内部依次做四件事：写出 codegraph 配置、建或更新索引、
把 Python 写在函数体内的 docstring 回填进索引、规则校验。**第一次跑会自动建索引**，所以首次的输出里
图规则（R1/R2/R3/D1）才有结果。

建索引是同步等完的，所以正常情况下同一次运行就能看到图规则。
如果输出里说「未找到索引」，那是建索引没成功——codegraph 没装、超时、
或者报错了。看 `sync` 那行写的是什么，先解决它，重跑并不会自己好。

**不要单独运行 `codegraph sync`。** sync 会把变动文件在索引里的记录整个删掉重建，
清空回填结果，注释会从索引里静默消失。

### 你（agent）加 `--json`

拿到一个 JSON 对象，直接读字段，不要从文本里猜：

    findings[]        每条 {rule, file, line, name, message}
    summary           {规则: 条数}
    total             findings 的条数
    rules             {规则: 一句话说明}
    exit_code         0 / 1 / 2

下面这几个不是审计发现，是**这次运行的环境信息**——用来说明「这份结果是在
什么条件下产生的」：

    project           项目根的绝对路径
    git               {branch, head}；不是 git 仓库时为 null（C1 也不会跑）
    sync              建/同步索引的一行状态；--no-sync 时为 null
    index_present     false 表示没建索引，R1/R2/R3/D1 已跳过
    backfilled        这次回填了多少条 docstring
    codegraph_config  写出 codegraph.json 的一行状态；没改动就是 null
    reports           {markdown: 路径, json: 路径}

**条数和上次对不上时，先看这几个字段再下结论。** 从 20 条掉到 7 条，
可能是修好了，也可能是 `sync` 写着「codegraph 未安装」、`index_present`
为 false，四条图规则根本没跑。没有它们只能靠猜。

`project` 值得确认一眼：配置文件是向上找的，monorepo 里可能落在你没想到的层。
`git` 说明这份报告属于哪个分支、哪次提交——同一个 `audit.md` 在不同分支上
内容不同。`codegraph_config` 非 null 说明这次改了索引配置，**下次结果可能变**。

不加 `--json` 是给人看的分组文本，向用户展示时用那个。

**退出码 0 的准确含义是「已执行的检查没有产出 finding」**，不是"全部合规"——
没建索引时 R1/R2/R3/D1 根本没跑。看到 0 先确认 `index_present` 是不是 true。
1 表示有 finding，2 表示项目未启用或配置损坏（此时输出只有 `error` 和
`exit_code` 两个字段，**不会生成报告**）。

### 报告文件

每次跑完在项目的 `.codegraph/` 下**覆盖写**两个文件：`audit.md`（给人看，
可直接打开）与 `audit.json`（内容与 `--json` 的 stdout 相同）。不留历史，
不与上一次比较——报告反映的是本次运行。

**没有索引的那次运行同样覆盖**，但报告会在三处标明不完整：标题行的条数后面、
正文开头的横幅、以及概览表里把 R1/R2/R3/D1 显式列成「未执行」。
这一点很要紧：条数从 20 掉到 7 不是问题变少了，是四条规则没跑。

向用户汇报时把 `audit.md` 的路径一并给出。

## 十一条规则

| 规则 | 判定 | 通常怎么处理 |
|---|---|---|
| R0 | 缺 docstring 或角色标记 | 补上，一行也算合格 |
| R1 | 审计范围内找不到调用它的地方 | **入口函数会被报**，先确认是不是对外接口；私有函数则大概率是死代码 |
| R2 | `[一次性]` 不在最外层 | 移到最外层目录，不是删除 |
| R3 | 主线调用了旁支 | **需要判断，见下** |
| R4 | `def` 那一行有的参数，Args 里没写 | 补 Args 条目 |
| R5 | 有返回值或 `yield`，但没有 `Returns:` / `Yields:` | 补上 |
| R6 | Args 里写了 `def` 那一行没有的参数 | 改参数时漏改了文档，同步过来 |
| D1 | 内层引用外层 | **模块化崩坏的信号**，见下 |
| D2 | 输出区目录存在但未被 `.gitignore` 忽略 | 建议用户在`.gitignore`加一行 `runs*/` |
| D3 | 写盘点写死了输出路径 | 在脚本入口定一次 `out`，写盘改成 `out / "文件名"` |
| C1 | 改了已有函数却没加 `变更:` 行 | **需要判断，见下** |

### 什么情况下规则不跑

看不到某条规则的告警，先确认是不是本来就跳过了：

- **最外层豁免输入输出规则和 R1。** 最外层（`layers` 的最后一项）的文件
  只查 R0，不查 R4/R5/R6，也不查零调用者——那一层装的就是一次性脚本，
  没有调用者是常态。那里的一次性代码不会被别人调用，逐参数介绍是负担。
  严格度随层级递减，越靠核心要求越严。
- **第三方代码**（`vendored`）跳过全部注释规则和 R1/R2，也不会作为 R3 的
  调用方被报，但仍参与 D1 和 C1。
  注意 R3 只看调用方是不是我们的代码：我们的主线函数调了一个 `vendored` 里
  带 `[旁支]` 标记的函数，照样报——问题出在我们这边。
- **Python 特殊方法不查。** 两端都是双下划线的方法——`__init__`、`__call__`、
  `__len__`、`__enter__` 这类——注释规则(R0/R4/R5/R6)和 C1 都跳过。
  它们的行为由语言规定：`__init__` 的参数就是构造参数，`__len__` 必然返回长度，
  调用方是解释器而不是你的代码。**不要给它们补 docstring**，审计不会因此变绿。
  R1 也跳过它们，判据略宽一点，`__mangled` 这种只有开头双下划线的也一并跳过。
- **没有 docstring 的函数只报 R0**，不再叠加 R4/R5/R6——连注释都没有时，
  再报三条是噪声。
- **R2 需要声明 `layers`**；**D1 需要 `layers` 或 `vendored`** 其中之一。
  都没声明就静默跳过——我们只校验用户自己声明过的东西。
- **R1/R2/R3/D1 依赖索引。** 索引由命令自动建立；仅在第一次运行、
  或 codegraph 未安装时会缺席，此时这四条跳过，JSON 里 `index_present` 为 false。
- **C1 依赖 git。** 不是 git 仓库、或文件未被跟踪时静默返回空。
- 语法错误的文件整个跳过——语法该由解释器和 linter 报。

### 几条已知的偏差

**R1 说的是「审计范围内找不到调用它的地方」**，不完全等于「没人用」。
最外层的整层、以及标了 `[一次性]` 的函数都豁免——它们按定义就没有调用者，
报出来只是噪声。实验输出区里的引用也不算数(那里本不该有代码)。codegraph 不跟踪
`import X as Y` 的别名，只通过别名到达的函数会被误报。看到 R1 先 grep 一下
`import .* as`，别急着删。反过来，`[一次性]` 标记的函数已从 R1 豁免——
它们按定义就没有调用者。

**R5 只看 `Returns:` 或 `Yields:` 在不在**，不检查写的内容和函数行为对不对得上。
普通 `return` 配一个 `Yields:` 也能过。

**D2 不是完整的 gitignore 解析。** 它逐行比对目录名和末尾 `*`，不处理 `!` 否定、
`**` 通配、子目录里的 `.gitignore`。所以它的判断可能和 git 的实际行为不同，
拿不准就跑 `git check-ignore -q runs/` 确认。

**R4 与 R6 成对出现时**，通常是一次参数改名没同步文档——两条从两侧指向同一处。

第三方代码被 D1 报「第三方代码 --imports--> ovam/...」，意味着官方代码被改成
依赖了我们的代码，以后没法跟上游同步。修法是把依赖反过来：让我们的代码去调它。

## R3 需要人的判断

R3 报「主线 X 调用了旁支 Y」。这不是错误，是提问：**本次实验用得到 Y 吗?**

读 Y 的正文来裁决。若正文说明它在等某个计划中的对照组，就留着;
若正文只是复述摘要、说不出它为什么在那儿，那它多半就是试错留下的残骸。

裁决结果有三种：留下(不动)、改标记为 `[一次性]` 并移到最外层、直接删除。
**删除前先确认它不在实验计划里**，这一步不要替用户做主。

## D1 需要动结构

D1 报「[ovam] --imports--> [scripts]」意味着核心层依赖了脚本层。
两种修法：被引用的那段代码如果是通用的，下沉进核心层;
如果是脚本专属的，说明核心层不该调它，改引用方。不要靠改 `layers` 顺序糊弄过去。

## 冗余代码：五类标签，每条必须给替代方案

上面十一条规则查的是注释与结构。**代码本身的冗余靠读，不靠规则** —— 边读边按这五类标：

| 标签 | 抓什么 | 必须附带 |
|---|---|---|
| `delete:` | 死代码、没人调用的"灵活性" | —— 直接删 |
| `stdlib:` | 手搓了标准库已有的东西 | **点名该用哪个函数** |
| `native:` | 重复了框架/运行时已有的能力 | 点名该用哪个 |
| `yagni:` | 只有一个实现的抽象、没用的配置、只有一个调用者的层 | —— |
| `shrink:` | 同样逻辑可以更少行 | **写出压缩后的样子** |

一行一条：`<文件>:L<行>: <标签> <问题>。<替代>。`

    models/loader.py:L34: shrink 27 行的校验类。邮箱查 '@',一行。
    utils/io.py:L12: stdlib 手写的路径拼接。用 pathlib.Path。

**只看多余复杂度，不看正确性、安全、性能** —— 那些归常规 review。
写不出替代方案的就别报，"这里有点复杂"对人没用。

## 顺手查一遍误入库的文件

`.gitignore` 只对未跟踪的文件生效，后加的规则管不了已经提交的东西。
注意加 `-C <项目根>`——审计命令不会改变你的当前目录，不加就可能查错仓库：

    git -C <项目根> ls-files -i -c --exclude-standard

列出的是「已入库但按现在的规则本不该入库」的文件 —— 多半是 checkpoint、
虚拟环境、索引目录。汇报时单独列出，并说明 `git rm -r --cached` 只影响
新提交，**历史里那份还在，仓库体积不会变小**;要彻底清除需重写历史，
那是得和用户商量的事。

## 绝不自动修改

**审计的产出是提案，不是补丁。** 逐条和用户过，得到确认才改。

科研代码尤其如此：**一段看着多余的逻辑，可能正是当初调出那个数的原因。**
一个奇怪的 `+1e-8`、一个"没人调用"的分支、一个多余的 `clamp` —— 删掉之后
论文里的数复现不出来，而且**不会报错**。等发现时已经不知道是哪一步改的。

所以：

- **不要批量修**，一条一条来
- **动之前先说清楚**这段代码可能在做什么、删了会影响哪个结果
- **拿不准就不动**，标记出来让用户判断
- **凡是碰到会进论文的数值路径，先跑一遍确认结果没变**

写代码时走一遍 `writing-minimal-code` 的四道决策，审计阶段要处理的就少。
在科研代码里，事前不写通常比事后删安全——因为删错了不报错。

## C1 要分清「别人依赖的东西变了」和「只动了内部」

C1 对比工作区与 `HEAD`，找出函数体变了、但 docstring 里 `变更:` 出现次数没增加的
函数。它先把代码解析成结构再比，而不是比文本，所以只改注释、只改缩进换行
不会误报——只有真正改了逻辑才算。比之前还会把 docstring 本身摘掉，
所以补写注释这个动作不会被算成改了代码。

报出来之后先判断改动的性质。**分界是调用方能不能感知到**——具体说是这四样：

    返回什么      类型、形状、值域、是不是已归一化
    抛什么异常    传非法值时报错，还是静默返回默认
    有没有副作用  写文件、改全局状态、改传进来的那个对象
    怎么调用      参数顺序、有没有前置要求（必须先调 setup()）

- **动了这四样里的任何一样** → 补一行 `变更:`，
  写清**原路径是否受影响** —— 读代码的人关心的不是你加了什么，
  是他原来依赖的那条路还在不在
- **纯内部重构**（调用方感知不到）→ 在汇报里说明一句「内部重构，未影响调用方」，
  代码不动。注意 **C1 只认 `变更:` 出现次数**，你的说明不会让它消失，
  下次跑仍然会报。这是预期行为，不要为了让它闭嘴而补一行没信息量的变更记录

**它漏掉的比误报的更值得注意：**

- **只比函数体，不比 `def` 那一行。** 加一个没用上的参数、改默认值、
  加装饰器、改类型注解，只要函数体没动，C1 一律不报
- **函数改了名、或挪进了别的类**，前后两版对不上号，会被当成新函数跳过
- 项目不是 git 仓库、或文件未纳入版本控制时，C1 静默返回空

所以 C1 是兜底，不是保障。它数的是 `变更:` 出现的**次数**，判断不了内容写得
对不对 —— 参数列表的改动和内容质量都得人看。

## 汇报

按规则分组，把 R3、D1、C1 和五类标签单独列出来并附上判断依据。
不要只丢一份清单——用户要的是「哪些该改、为什么、怎么改」，
不是「有 15 处不合规」。

除了规则的产出，还有三类东西值得在汇报里带一句，它们都**只是建议，
改不改由用户定**：

- 该声明而没声明的配置项（`layers`、`vendored`）
- 索引里明显多余的目录，或建索引明显变慢
- 已经入库但按现在的 `.gitignore` 本不该入库的文件

结尾说清两件事：机械规则报了几条、你自己读出来的冗余有几处。
不要合成一个「可删约 N 行」的总数——机械 finding 里没有行数信息，
凑出来的数字是伪精度。没发现值得改的就直说没有。
