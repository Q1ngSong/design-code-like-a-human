# 记录实验结果

**一次实验跑完，先记一行，再跑下一次。** 不记就跑下一次，二十轮之后
只剩一堆目录名和翻不动的终端输出。

## 一组实验一个 CSV

文件名跟着这组实验走，和分支名对得上 —— `experiments/lora_rank.csv`，
一行一次实验：

```csv
task,简介,指标,结论,输出目录,git 版本
rank8_lr1e-4,"rank 4→8，上轮已收敛未过拟合",FID 12.3 / CLIP 0.281,有效 +0.4 分,runs/ablation_study/lora_rank/rank8_lr1e-4,a1b2c3d
rank16_lr1e-4,继续加到 16 看还有没有收益,FID 11.9 / CLIP 0.283,收益递减 +0.1 分,runs/ablation_study/lora_rank/rank16_lr1e-4,4e5f6a7
rank32_lr1e-4,再翻倍确认拐点,FID 14.1 / CLIP 0.271,"过拟合，回退",runs/ablation_study/lora_rank/rank32_lr1e-4,8b9c0d1
```

字段里有逗号就加双引号，标准 CSV 写法。

`experiments/` 和 `runs/` 一样，**默认不入库**（`.gitignore` 加一行）。
记录是产物不是代码，跟着输出走；不入库也让 `git reset --hard` 碰不到它。

| 列 | 写什么 |
|---|---|
| `task` | **就用输出目录的叶子名**，`{参数}{值}{参数}{值}{参数}{值}......` 拼接 |
| `简介` | **为什么试这个**，不是「跑了个实验」 |
| `指标` | 你关注的那几个数，自由格式（`FID 12.3 / CLIP 0.281`） |
| `结论` | 有效 / 无效 / 回退 / 待定，加一句为什么，下一步做什么 |
| `输出目录` | `runs/` 下的路径，把这一行和实际产物钉在一起 |
| `git 版本` | 跑这次实验时的提交号，`git rev-parse --short HEAD` |

`task` 一列两用：既是这次实验设置的缩写，又是 CSV 和 `runs/` 之间的连接键。
所以直接用叶子目录名，别另起一个短名字——两套命名对不上，回头就得靠人脑映射。

    rank8_lr1e-4_round1     ← 一眼看出 rank 8、学习率 1e-4、第1轮(也可以r8l4r1等更短的缩写，来快速定位)
    runs/ablation_study/lora_rank/rank8_lr1e-4_round1/

只写**这一组里变化的**参数。不变的那些属于上一层（`lora_rank` 这个 setting
本身就说明了在调 rank），塞进叶子只会让每个名字都又长又一样。
如果一组里有五六个参数在动，那多半不是一组实验，该拆。

`git 版本` 那列是为了**回到当时的代码**：`git checkout <提交号>` 就能重跑这一行。
参数在叶子目录名和简介里，代码在提交号里，两样凑齐才能复现。
没有它，三个月后你只知道「rank8 得了 12.3」，不知道那时的 loss 函数长什么样。

这一列还有个作用：正因为每次实验都钉住了代码版本，改既有函数才不那么可怕——
改坏了能定位到是哪一次、能回到那个提交重跑（见 `writing-minimal-code`）。

**跑之前先确认工作区是干净的。** 有未提交改动时 `HEAD` 是骗人的——
`checkout` 回去拿到的不是当时真正跑的代码，这一列就失效了。

    git status --porcelain     有输出就说明还没提交

有改动就先 commit 再跑。实在要带着改动跑（试探性的一次），
在 `git 版本` 列里写成 `abc1234+dirty`，让读的人知道这一行复现不了。

**一组一个文件，不是一个全局表。** 并行分支各写各的，合并零冲突；
要总表就把 `experiments/*.csv` 全读进来。

「一组」有多大由你判断 —— 几次相关的调参是一组，换个方向就该另起一组。
没有硬标准，判据是：这些实验会不会放在一起比较。

## 失败的也要记

跑砸了、结论是「这条路不通」——**照样记一行**，结论写清为什么不通。

只记成功的实验，记录就是假的：三个月后看到一片「有效」，不知道中间试错过什么，
于是重新试一遍已经排除过的方向。在长程自动任务里这个损失最大，
因为没人凭记忆兜底。

## 没跑完的也一样

上一节说的是「跑完了但结论是负面」。**中途挂掉是另一回事**——OOM、数据缺失、
loss 变 NaN、机器被抢占——处理方式一样,三件事都要做:

**记一行。** 结论写清挂在哪一步、什么原因:

    rank64,"显存上限试探",—,"OOM,step 3200 挂,batch 8 时显存不够",runs/.../rank64,abc1234

指标列填 `—`,别留空:留空看着像忘了记,`—` 说明确实没有。

**半成品目录留着,并照常填进输出目录列。** 崩之前的部分往往就是证据 ——
loss 曲线到崩溃点为止已经能看出是发散还是显存问题。删掉就只剩一句
「OOM」,下次还得再撞一次才知道在哪一步。

**照常 commit。** 失败也是一次决策的结果,跳过 commit 会让 `git 版本` 那列
指向一个和实际跑的代码对不上的提交 —— 整列就此失效,后面所有行都不可信了。

## 什么时候写

**跑完立刻写，在决定下一步之前。** 顺序反了就会变成「先想下一步、
顺手补记录」，而补的记录一定是事后合理化，不是当时的判断。

这组收尾时（合并前）在 CSV 末尾或 commit message 里写总结论：
哪个配置胜出、为什么、下一轮打算做什么。

## 关于格式

上面的列和文件名是模板。项目已经在用别的记录方式（自己的表格）就跟着它走，
别为了统一去改人家的习惯。**要保留的是「跑完先记再跑下一次」这个习惯，
不是这几个列名。**
