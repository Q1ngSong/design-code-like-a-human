# 动手之前

两个目标：让读代码的人负担最小，让这次的改动总量最小。

这两件事经常被搞反。为了「不动旧代码」而不断新加函数、加包装层，不是改动
变小了，是改动换了个地方堆着——同一件事最后有两个函数各做一半，反而更难读。

科研代码还有一层：删除比在别处危险。一段看起来多余的逻辑——某个 `clamp`、
某个奇怪的 `+1e-8`、一个没人调用的分支——可能正是当初调出那个数的原因。
删掉之后论文里的数变了，而且不报错。


## 先把情况看清楚

动手前弄清楚这几件事，它们都能验证：

- **谁会用它。** 代码里已有的调用方直接找出来，可能不止一个；如果它本身就是
  入口（CLI 子命令、实验脚本、被外部调度的任务），写明由谁触发。
  下文统称**用处**。
- 输入从哪来、输出被谁消费、错误往哪传
- 现有实现和已装依赖里有没有能用的

项目启用了规范的（根目录有 `.comment-standard.json`），先刷新一次（第一次会自动建索引），再查：

    python3 ../../scripts/refresh.py <项目根> --base HEAD    先跑这个;项目没进 git 或还没有 commit 就去掉 --base
    codegraph explore <关键词>     相关符号的源码 + 调用链 + 波及面，一次拿到
    codegraph query <名字或说法>   按名字或注释内容搜，看看是不是已经有了
    codegraph callers <函数名>     谁在调它
    codegraph impact  <函数名>     改它会影响什么

`scripts/refresh.py` 在插件根下，路径**相对本技能目录**。调用本技能时
你已经被告知它的**基准目录**，把这个相对路径接在基准目录后面写成绝对路径再跑，
不要靠当前工作目录去拼。

**刷新这一步不能省，也不能用 `codegraph sync` 代替。** codegraph 抓不到
Python 写在函数体内的 docstring，索引里那一列是空的；审计命令在 sync 之后
把它们补回去。跳过这一步，`query` 就搜不到任何按注释内容的匹配——你会以为
项目里没有现成的实现，转头造一个重复的。

而且 `sync` 是**按文件整体删除重建**：改过一个文件，该文件里所有函数的注释
都会从索引里消失，连没动过的那些也一样。所以每次改完代码都要重新刷新，
不是只在第一次。

没启用规范的项目退回 `grep -rn` 和读文件，慢一点，但这一步不能跳。

**「现有实现里有没有能用的」必须真去搜，不能靠印象。** 这条最常被跳过，
也最容易造出重复实现：项目里明明有个 `_normalize`，又写了一个
`normalize_maps`，两个都在，谁也不敢删。

搜的时候注意：全文检索把连续的汉字当成一个整体、只能从头匹配，`归一化` 找不到
「把权重聚合并归一化到」中段的那三个字。**用英文术语搜更可靠**（英文天然被
空格切开），或者换几个说法多试一次。

要改既有代码的，还要看依赖它的地方：

`codegraph explore` 的输出里有一段叫 `Blast radius`（波及面），列出依赖它的位置，
以及若干跳之内能到达的测试文件。**这个结果不保证完整**——跨文件解析是
尽力而为，动态调用、依赖注入、`import X as Y` 的别名都可能漏掉。把它当成
起点而不是清单，改动关键路径时再 grep 一遍函数名。那一段里列出的测试
文件也只说明「有测试碰得到」，不代表你要改的那条分支被测过。

调用方的数量不是风险指标。一个调用方可能是对外接口，十个同质的内部调用
反而好改。真正要看的是**它们依赖的是什么**：返回值形状、异常行为、副作用、
调用顺序。

## 第一道：该不该存在

**没有当前用途的东西不写。** 这是个闸门，不通过就到此为止，后面三道都不用问。

科研代码里最常见的多余，是为还没发生的实验提前铺路：留一个 `model_type`
分派、抽一个 scheduler 基类、加一个「以后可能要换」的配置项。等真的要换时，
需求形状往往和当初设想的不一样，那层抽象反而挡路。

说不出用处的，就是还不需要。

## 第二道：能不能改现有的

**改动大小按 diff 算，不按「碰没碰旧文件」算。** 给原函数加三行判断，
通常比新写一个二十行的变体小得多。

新写一个函数不是零成本。它是多出来的一处要读、要维护的东西，而且和原版
会慢慢漂移。包一层尤其如此：读的人要同时理解包装和被包装的两份逻辑，
比看一个改过的函数更费劲。

### 改原地在这里更安全

产品代码里不敢轻易改既有函数，是因为线上出问题不好定位。科研代码不一样：
实验记录里有 git commit 和参数（见 `recording-experiment-results`），
改出问题能定位到是哪一次、能回到那个提交重跑。

所以不必为了「万一破坏调用方」绕开修改。该确认的还是要确认——看清楚调用方
依赖的是返回值形状、异常行为还是副作用——但确认完就直接改，不用另起炉灶。

### 什么时候才该新写

三种情况：

**老路径还要能跑。** 做对照实验时基线和新方法都得能跑，这时不能把老逻辑
改掉。共用得多就给原函数加一个参数分支，几乎不共用才分开写。

**新东西确实是另一件事。** 不是原来那件的变体，只是恰好在附近。硬塞进原函数
会让它有两个不相干的职责。

**改原地会波及一堆本不需要变的调用方。** 比如为了一个新场景改掉返回值形状，
其余十个调用方都得跟着改。这时加参数或加一个薄包装更划算。

除此之外，倾向于改原地。

## 第三道：新写的话，代码从哪来

按顺序看，能满足就用它，不再往下：

1. **代码库里已有的。** 用之前确认语义真的一致——名字像不代表行为一样，
   边界处理尤其容易不同。如果现有实现耦合了不相关的东西，复制一小段比
   强行复用更干净。
2. **标准库。** 例外是标准库方案明显更绕，比如为了套一个通用接口写出三层适配。
3. **已装依赖。** 不必为一个小功能引新包。但要确认这个包适合当前这条执行路径：
   只在测试里用过的包，不要直接放进训练主循环。
4. 都没有，自己写。

## 第四道：写成什么样

**最小可行 = 让已确认的用处拿到它们需要的结果，并且不改变其他调用方的行为。**
空实现和「能跑不报错」都不算。在这个前提之上：

- 不加没有调用点的参数、分支、配置项
- 不为单一实现抽接口或基类
- 一个清楚的表达式能写完的，不抽成函数

反过来，如果压缩之后需要读两遍才懂，或者把错误处理藏进了链式调用，
就保持展开。行数少不是目标，能看懂才是。

**写出来的每个函数都要有 docstring，特殊方法（`__init__` 这类）除外。**
格式、角色标记、`Args` 里该写什么、哪一层可以少写，见 `writing-python-comments`——
那份是查询用的，写的时候翻一下。
项目根没有 `.comment-standard.json` 的，按项目自身惯例写。

## 不要为了简洁删掉的东西

以下几类看起来像多余的防御，实际不是：

- **随机种子的设置与记录。** 删掉之后结果不可复现，而这通常要到复现失败时
  才发现。

- **train / test 边界的隔离。** 简化掉就是数据泄漏。它不报错，指标还会变好看，
  是最难自查的一类错误。

- **数值稳定性处理**，如 `eps`、`clamp`、`nan_to_num`。它们经常没有注释，看着
  像随手加的，但去掉之后数值会悄悄偏移。真要动，先固定随机种子、用同一批
  输入跑一遍，对比论文里用到的那几个指标。

- **防数据丢失的错误处理。** checkpoint 写入失败要抛出，不要吞——调用方需要据此
  中止训练，否则会在无效状态下继续跑。

- **信任边界上的输入校验**：命令行参数、配置文件、外部数据文件。

- **用户明确要求的功能**，即使你认为它不必要。

不在清单里的普通代码，删除判据是**没有任何调用方**——审计规则 R1 会把这类
函数列出来。注意入口函数天然没有调用方，先确认它是不是对外接口。

清单之外的兜底、`try/except` 和参数校验，先查清楚它防的是什么：翻一下 git 记录，
或者看调用方会不会传出那种输入。查清楚了再决定删还是留。**实在查不清就留着，
并就近写一行注释说明「不确定这个分支是否仍然需要」**——分支本身没有 docstring，
注释写在它上面；整个函数存疑的才写进 docstring。留一个待办，
好过留一段没人敢碰的代码。

## 改了既有函数，记一行

如果改动影响了调用方能依赖的东西——返回值、异常、副作用、性能量级——
在 docstring 里加一行：

    变更: YYYY-MM-DD 未知名称改为直接报错，原兜底返回 ddim 的分支已移除。

重点写**原来那条路还在不在**。读代码的人多半不是来看你加了什么，
而是来确认他依赖的东西有没有动。

**这不是变更日志。** 只记影响调用方的改动。纯内部重构——重命名局部变量、
提取一个私有辅助函数、改写等价的条件表达式——不必写，否则 docstring 会积满
与当前行为无关的历史。

注意「纯内部」比看上去窄。调整循环顺序就常常不是：它可能改变副作用发生的
次序、输出顺序、异常抛出的时机，浮点累加的结果也会变。拿不准就当成调用方能感知到。

新增的函数不写。它的 docstring 已经完整描述了当前行为，不存在
「原来那条路」的问题。

**审计规则 C1 会查这条**,但它只是兜底:比对 `HEAD`(带 `--base` 时是那个 ref)找出签名或函数体变了、
`变更:` 却没增加的函数。它数的是次数,判断不了内容——「第二道」里加参数那种
改动它会报,但报了不等于你写对了,写一行没信息量的也能让它闭嘴。
所以别指望它替你判断,该写的时候就写清楚。

规则的完整行为与处置见 `auditing-code-comments`。

## 要改的地方太多时

如果发现加一个功能得改五六处，先停下来问一句再动手。

有时这是合理的：横切功能、协议实现、数据迁移，本来就会碰很多地方。
有时是接口划分和当前需求对不上，值得先调整结构再加功能。

这两种情况从改动数量上分不出来，也没有可靠的判据能自动区分——坏的接口划分
同样会让每一处改动看起来都合理。所以这里不给判据，只要求**停下来把这五六处
列给用户看**，让他判断是照做还是先调结构。不要自己决定重构。

**这条只在构建期。** 快速迭代期（见 `running-experiments-on-branches`）没人可问，
自己定——但四道闸门一道不少：该不该存在、能不能改现有的、代码从哪来、
写成什么样。天平是同一架：五六处改动是同一个想法的自然延伸就做；
是在绕一个不合适的接口就不做，换个想法试。快速迭代里改错了 stash 掉很便宜，
但一次尝试变成一次重构，跑出来的数字就说不清是想法有效还是结构变了。

## 做完给用户回复

代码先行。之后只说两件事：这次**没做**什么，以及什么条件下该补上。
做了什么代码本身已经写着，不用复述。

无人值守（`audit.json` 的 `unattended` 为 true）时没人读回复。同样这两件事
写进这一轮的记录——`recording-experiment-results` 的 `结论` 列，或 commit
message——别丢。这时「先把情况看清楚」里那次刷新（带着 `--base HEAD`），只看
`changed=true` 的 finding 和 `unindexed_files`：存量告警每轮都一样，不用重读。
快速迭代里动手前工作区是干净的，`changed=true` 为空是正常的，不是漏了。

这是给用户看的回复，不是代码注释——注释该写什么在 `writing-python-comments` 里。
