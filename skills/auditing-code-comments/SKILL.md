# 审计注释、边角料与分层

用在**功能已经跑通之后**。功能没通就先去把功能弄通 —— 对着不工作的代码
做审计是浪费。例外是快速迭代的**跑前审计**（`running-experiments-on-branches`）：
`--base HEAD` 只看这次改动上的告警，为的是在烧 GPU 之前抓到 D3 这类错。

## 前提

项目根需有 `.comment-standard.json`。没有则该项目未启用——
**先问用户要不要启用，不要自作主张创建。**

这个文件里的每一项都是用户的声明，不是你的判断：

| 键 | 声明的是 | 影响 |
|---|---|---|
| `layers` | 哪些目录构成依赖层，由核心到外围；一层可以有多个平级目录，写成列表 | 不写则 R2 跳过；D1 只要声明了 `vendored` 也会跑 |
| `vendored` | 哪些目录是复制进来的第三方代码 | 不写则那些代码会被当自己的审 |
| `output_roots` | 实验输出区的目录名，列表 | 默认 `["runs"]` |
| `codegraph` | 索引范围的加减 | 见 `references/setup.md` |

`output_roots` 一律写成列表，只有一个也是：

    "output_roots": ["runs"]
    "output_roots": ["runs", "outputs", "logs"]

真实项目常同时有几个输出目录，换过根的（`runs` → `runs-v2`）两个也都还在。

最小配置是 `{}`。这时 R0/R1/R3/R4/R5/R6/C1 照常跑，只有依赖层级相关的
R2、D1 跳过；默认输出区 `runs/` 存在的话 D2 也会跑。

**你不改这个文件。** 审计时发现该声明而没声明的，在汇报里说明理由和建议写法，
由用户决定。两种最常见的：

- 项目明显有分层结构（核心包、脚本目录、临时脚本），但没写 `layers`——
  建议写上，能启用 R2 和 D1
- 有复制进来的官方代码（如 `sd15/`），但没写 `vendored`——那些函数会被大量
  报 R0，而它们本来就不该按我们的标准写注释

首次启用要配 `layers`、想弄清索引范围、或要查误入库的文件——见 `references/setup.md`。

## 无人值守

无人值守 = `.codegraph/unattended` 这个哨兵存在且不超过 24 小时。`audit.json` 的
`unattended` 字段和会话开头 hook 的「无人值守中」都是它的快照，平时看这两处就够；
快照可能落后（人回来 rm 了哨兵、还没重跑审计），拿不准就 `cat` 一下哨兵本身。
**除此之外不要自己推断。** 怎么设、怎么清见 `running-experiments-on-branches`。这份技能里凡是写着「交给用户」「让用户决定」
「先问一句」的地方，无人值守时统一这样办：

- **不问。** 没人可问，问了就是卡住。
- **不改。** 不建 `.comment-standard.json`、不动 `codegraph` 配置、不删文件、
  不拿存量 finding 去改代码。落在这次尝试上的告警（`changed=true`）归驱动层的
  规矩管——README 的例子里 D3 改掉再跑、R1 删掉。审计的产出本来就是提案不是补丁，
  无人值守只是把「等确认」改成「不确认就不动」。
- **不拦。** 退出码 1 不是停下的理由。findings 在 `audit.json` 里，
  驱动层（你的 `program.md`、ARIS 的循环）决定处理哪几条、忽略哪几条。
- **自己定的留一行为什么。** 不问不等于不留痕：本该问的地方你选了什么、为什么，
  写进 commit message 或 CSV 的简介/结论列。不许「问一句，没人答就继续」——
  要么阻塞地问，要么不问；一旦交出 turn，沉默不会让工作流继续。
- **该问的那几类留在报告里就够了。** 启用与否、`layers` 怎么声明、R3 该留该删、
  误入库的文件要不要移出——这些在快速迭代里每轮都一样，不会因为多跑一次
  就变。人回来之后跑一次 `refresh.py`，`audit.md` 就是待办清单，不用另外攒。

两条底线不因无人值守放松：

- **退出码 2 不是 finding，是审计本身没跑成**（配置损坏、`--base` 的 ref
  不存在）。写进这一轮的记录，实验循环照常——但别把它当成「审计通过」。
  连续几轮都是 2 就不再调审计，每轮记一句「审计不可用」，**实验照跑**——
  停的是审计不是循环。人回来看到那一串就知道环境有问题。
- **「不要为了简洁删掉的东西」那张清单**（`writing-minimal-code`）无人值守时
  反而更硬：有人在场删错了当场能问，没人在场删错了要到复现失败才发现。

有人在场时照旧：一条一条过，得到确认再动。

## 运行

    python3 ../../scripts/refresh.py <项目根> --json


**差异审阅加 `--base <ref>`**:审计仍是全仓库的,但报告会把落在改动上的告警——
改了签名、体或 docstring 的函数、新文件(含还没 `git add` 的)、改动文件里的模块级语句——
单独列成「本次改动」一段,放在「存量」前面。抓不到的是图效应:删了调用点让
别处没动的函数新报 R1,那种落在「存量」里。ref 怎么给:

| 场景 | ref | 为什么 |
|---|---|---|
| 快速迭代,跑前审计 | `HEAD` | 这次尝试还没 commit,工作区里就是它的改动 |
| 合并前检查 | `main` | 整条实验分支相对主分支的改动;C1 也比 main,整条分支改了没记的都报 |
| 有人在场,想看某两个分支之间 | 人指定,如 `--base develop` | 用户自己说比什么 |
| 省略 | —— | 全仓库审阅,不分段;C1 仍比工作区 vs HEAD |

ref 不存在时退出码 2,`error` 字段说明。
`scripts/refresh.py` 在插件根下，路径**相对本技能目录**。调用本技能时
你已经被告知它的**基准目录**，把这个相对路径接在基准目录后面写成绝对路径再跑，
不要靠当前工作目录去拼。

这一条命令内部依次做四件事：写出 codegraph 配置、建或更新索引、
把 Python 写在函数体内的 docstring 回填进索引、规则校验。**第一次跑会自动建索引**，所以首次的输出里
图规则（R1/R2/R3/D1）才有结果。

建索引是同步等完的，所以正常情况下同一次运行就能看到图规则。
如果输出里说「未找到索引」，那是建索引没成功——codegraph 没装、超时、
或者报错了。看 `sync` 那行写的是什么，先解决它，重跑并不会自己好。

**不要单独运行 `codegraph sync`。** sync 会把变动文件在索引里的记录整个删掉重建，
清空回填结果，注释会从索引里静默消失。

`--json` 每个字段的含义见 `references/handling.md`。

### 报告文件

每次跑完在项目的 `.codegraph/` 下**覆盖写**两个文件：`audit.md`（给人看，
可直接打开）与 `audit.json`（内容与 `--json` 的 stdout 相同）。不留历史，
不与上一次比较——报告反映的是本次运行。

**没有索引的那次运行同样覆盖**，但报告会在三处标明不完整：标题行的条数后面、
正文开头的横幅、以及概览表里把 R1/R2/R3/D1 显式列成「未执行」。
这一点很要紧：条数从 20 掉到 7 不是问题变少了，是四条规则没跑。

向用户汇报时把 `audit.md` 的路径一并给出。

## 规则

| 规则 | 判定 | 通常怎么处理 |
|---|---|---|
| R0 | 缺 docstring 或角色标记 | 补上，一行也算合格 |
| R1 | 审计范围内找不到调用它的地方 | **入口函数会被报**，先确认是不是对外接口；私有函数则大概率是死代码 |
| R2 | `[一次性]` 不在最外层 | 移到最外层目录，不是删除 |
| R3 | 主线调用了旁支 | **需要判断**，见 `references/handling.md` |
| R4 | `def` 那一行有的参数，Args 里没写 | 补 Args 条目 |
| R5 | 有返回值或 `yield`，但没有 `Returns:` / `Yields:` | 补上 |
| R6 | Args 里写了 `def` 那一行没有的参数 | 改参数时漏改了文档，同步过来 |
| D1 | 内层引用外层 | **模块化崩坏的信号**，见 `references/handling.md` |
| D2 | 输出区目录存在但未被 `.gitignore` 忽略 | 建议用户在`.gitignore`加一行 `runs*/` |
| D3 | 写盘点写死了输出路径 | 在脚本入口定一次 `out`，写盘改成 `out / "文件名"` |
| C1 | 改了已有函数却没加 `变更:` 行 | **需要判断**，见 `references/handling.md` |

某条规则报了或没报都可疑时——什么情况下规则不跑、已知偏差、R3 / D1 / C1 怎么判断、
冗余代码的五类标签——见 `references/handling.md`。

## 绝不自动修改

**审计的产出是提案，不是补丁。** 逐条和用户过，得到确认才改。

科研代码尤其如此：**一段看着多余的逻辑，可能正是当初调出那个数的原因。**
一个奇怪的 `+1e-8`、一个"没人调用"的分支、一个多余的 `clamp` —— 删掉之后
论文里的数复现不出来，而且**不会报错**。等发现时已经不知道是哪一步改的。

所以：

- **不要批量修**，一条一条来
- **动之前先说清楚**这段代码可能在做什么、删了会影响哪个结果
- **拿不准就不动**，标记出来让用户判断
- **凡是碰到会进论文的数值路径，先跑一遍确认结果没变**

写代码时走一遍 `writing-minimal-code` 的四道决策，审计阶段要处理的就少。
在科研代码里，事前不写通常比事后删安全——因为删错了不报错。

## 汇报

按规则分组，把 R3、D1、C1 和五类标签单独列出来并附上判断依据。
不要只丢一份清单——用户要的是「哪些该改、为什么、怎么改」，
不是「有 15 处不合规」。

除了规则的产出，还有三类东西值得在汇报里带一句，它们都**只是建议，
改不改由用户定**：

- 该声明而没声明的配置项（`layers`、`vendored`）
- 索引里明显多余的目录，或建索引明显变慢
- 已经入库但按现在的 `.gitignore` 本不该入库的文件

结尾说清两件事：机械规则报了几条、你自己读出来的冗余有几处。
不要合成一个「可删约 N 行」的总数——机械 finding 里没有行数信息，
凑出来的数字是伪精度。没发现值得改的就直说没有。
