# 首次启用:layers、索引范围、误入库文件

首次启用、调整索引范围，或检查误入库文件时，阅读对应章节。

## 怎么判断 layers 该怎么写

用户第一次启用时多半不知道填什么。**先看目录结构再给具体建议，
不要甩一句格式让他自己填。**

    ls <项目根>
    codegraph query <某个核心符号>      有索引的话看看谁依赖谁

判据只有一条:**谁离不开谁**。几个包同为核心、说不出谁上谁下的，放同一层。

- **最内层**是拿掉它别的就跑不了的那个 —— 通常是同名于项目的包
  (`ovam/`、`src/<项目名>/`),或者放模型、算法主体的目录
- **最外层**是拿掉它主体照常跑的 —— 临时脚本、探针、`temp_scripts/`、`sandbox/`
- **中间层**是调用核心、又被外层调用的 —— 评测、训练、`scripts/`、`tools/`

判不准就问一句:「拿掉 `scripts/`,`ovam/` 还能用吗?反过来呢?」
答案通常一秒就出来。

### 常见形态

| 项目长这样 | 建议 |
|---|---|
| `ovam/` + `scripts/` + `temp_scripts/` | `["ovam", "scripts", "temp_scripts"]` |
| 核心两个包平级（`ovam/` 和 `erase/`），脚本按模型分成两个目录 | `[["ovam","erase"], ["scripts_sd15","scripts_sdxl"], "temp_scripts"]` —— 列表就是一层，任何一层都可以；同层互通，内层不能依赖外层 |
| 只有一个包 + 根上几个脚本 | `["<包名>"]` —— 根上的脚本不分层,自动跳过校验。**单层就是核心,不享受最外层豁免**,R1/R4/R5/R6 照跑 |
| 全平铺,没有目录结构 | **别写 `layers`**。分层是描述现状,不是强加结构 |
| 分不清中间层 | 先写两层 `["核心", "外围"]`,跑一轮看 D1 报什么再细分 |

**层不必覆盖所有目录。** 没进任何层的路径跳过层级校验 —— 那是「没说」,
不是「错了」。宁可少写一层,也不要为了凑齐而硬塞。

**顺序错了比不写更糟。** 写反了会把正常的依赖全报成违规,用户第一次跑就
看到满屏 D1,多半直接把配置删了。拿不准顺序就先只写最内层那一个——
这样没有最外层,核心层按最严的标准查,不会漏。

## 索引范围：你只看，不改

索引哪些目录是用户的决定，写在 `.comment-standard.json` 的 `codegraph` 键里。
**不要自己去改它**，也不要因为觉得某个目录没必要索引就动手加 `exclude`。

你能做的是观察并报告。建完索引看一眼实际收了什么：

    sqlite3 <项目根>/.codegraph/codegraph.db "SELECT path FROM files;"

发现明显不该在里面的东西——复制进来的整个权重仓库、几万行的 notebook 导出、
建索引明显变慢——**在汇报里说一句**：哪个目录、多少文件、建议排除。
让用户决定改不改。

多索引一点通常无害：`explore` 和 `callers` 还能找到那些文件。
但注意它们**会**参与注释规则和 R1——只有层级规则（R2/D1）要求文件属于
某个已声明的层。所以多出来的目录会带来多余的 R0 告警，这也是值得报告的信号。

**审计范围和索引范围是两回事。** 审计按配置（`output_roots`、`codegraph` 的
include/exclude、`.gitignore`）遍历磁盘，不看索引；索引只服务查询和图规则。
索引落后于磁盘时新文件照样被注释规则审到，报告会在 `unindexed_files` 里
点名哪些文件图规则没查到——索引是辅助文件，不限制任何别的功能。

### 用户问起时的事实

**`include` 不是白名单。** 这是最容易误解的一点：两个键都是在默认结果上做加减，
没有「只索引这几个」的模式。

| 键 | 作用 |
|---|---|
| `exclude` | 从默认结果里**减掉**（能减掉已被 git 跟踪的目录，`.gitignore` 做不到） |
| `include` | 往默认结果里**加回**（把被 `.gitignore` 丢掉的源码拉回来） |
| `deprioritize` | 仍然索引，但在搜索里不抢排名 |
| `extensions` | 映射自定义后缀 |
| `includeIgnored` | 救回被 `.gitignore` 的**嵌套 git 仓库**（字符串列表）。只管上游索引，不影响审计范围；普通源码要拉回来用 `include` |

实测：五个目录的项目里写 `"include": ["ovam","scripts","temp_scripts"]`，
结果仍是 `Indexed 5 files`；换成 `"exclude": ["notebooks/","legacy/"]`
才变成 3 个。

`deprioritize` 适合 `temp_scripts/` 这种符号名和正式代码撞车的目录。

配置写在 `.comment-standard.json` 里，刷新时写出 `codegraph.json`，**一处维护**。
它是派生文件，每次刷新覆盖，手改留不住。

删掉配置里的 `codegraph` 段**不会**删除已生成的 `codegraph.json`——分不清它是
我们生成的还是用户自己写的，删掉是毁数据。这时命令会提示它还在、不再受管理。
看到这条提示就在汇报里带一句，让用户决定要不要删。

要撤掉之前的 `exclude`/`include`，不用删文件：把配置写成 `"codegraph": {}`，
空对象是显式的「回到默认」，下次刷新会把 `codegraph.json` 覆盖成空。

## 启用时把 .gitignore 补齐

启用项目时，检查 `.gitignore` 是否覆盖实验输出、本地配置和工具生成的文件。可参考以下模板：

```gitignore
# 实验输出（实验的中间产物，包括权重、生成内容、评估记录、评估报告等。） —— 换根后仍覆盖
runs*/
# experiments/ 不在这里：实验记录入库，它是结论不是产物

# 索引与派生的审计报告,删掉重跑就回来
.codegraph/

# codegraph 的项目配置。它必须放在项目根(codegraph 只在那儿找它),
# 但内容由 .comment-standard.json 的 codegraph 段生成,同样是派生物
codegraph.json

# 密钥与本地配置 —— 永远不要提交这部分内容，必须仔细审计
.env
.env.*
*.pem
*.key

# Python 产物与虚拟环境
__pycache__/
*.pyc
.venv/
venv/
.pytest_cache/

# 编辑器与系统
.vscode/
.idea/
.DS_Store
```

## 顺手查一遍误入库的文件

`.gitignore` 只对未跟踪的文件生效，后加的规则管不了已经提交的东西。
例如，补上 `runs/` 的忽略规则后，之前提交的 checkpoint 仍在版本库中。

用以下只读命令检查。`-C <项目根>` 指定要检查的仓库，避免因当前目录不同而查错位置：

    git -C <项目根> ls-files -i -c --exclude-standard

命令列出已跟踪、但按当前忽略规则应排除的文件，例如 checkpoint、虚拟环境和索引目录。

**把清单交给用户判断。** 可提供以下移出索引的命令：

    git rm -r --cached <路径>

**不要执行这条命令。** 它会改变 Git 的跟踪范围，哪些文件应保留需要用户确认；
看似中间产物的目录，也可能保存了论文图表的来源。提供文件清单、命令和影响说明后，
等待用户决定。无人值守时，将这些内容写入本轮记录（`结论` 列或 commit message），
继续实验循环，留待用户处理。

说明 `git rm --cached` 只让文件不再出现在**后续提交**里，**历史版本仍然保留，
不会因此缩小仓库体积**。彻底移除历史版本需要重写历史，例如使用 `git filter-repo`；
这会影响协作者，必须由用户决定。
