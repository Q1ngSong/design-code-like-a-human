# 公平对比：开跑前冻结对照协议

要比较两种以上方案时（新想法对旧方案、我们的方法对 baseline），跑任何实验之前，先在组 README 里写一节
「对照协议」，单独提交一次：`freeze(<组>): 对照协议`。协议提交在前、结果在后，git 历史能证明规则不是看了结果才定的。
之后再用 `exp-plan` 登记第一个实验。

每次尝试怎么记、组结论怎么写，仍按 `recording-experiment-results`；这里只管对比本身的规矩。

```markdown
## 对照协议
- 对照方: new, old
- 训练条件: configs/train_v3.yaml（数据 v3，200 epoch，seed 0/1/2）
- 调参: 每方自动调参 20 次（用户 2026-09-23 确认）
- 正式测试集: data/coco5k/
```

| 字段 | 写什么 |
|---|---|
| 对照方 | 参与比较的方案名，至少两个。CSV 每一行的 `简介` 以其中一个名字开头，如 `old: 新条件下重训` |
| 训练条件 | 双方共用的配置文件、数据版本、epoch、种子 |
| 调参 | 每方调几次，以及是谁定的，写法见下文 |
| 正式测试集 | 测试集所在的路径；只测其中一部分时加 `N=数量`，不写 N 就是整个路径都要测。一般从上级 README 继承，见下文 |

## 旧方案也要重训

训练条件和旧方案当初训练时有任何不同，旧方案现成的权重就不能拿来比较，哪怕它是单独调优过的最好版本。
只让新方案按新条件训练，比出来的差距分不清来自方法还是来自条件，而且不会报错。
所以每一方都要在本组按协议的条件重新跑，在本组 CSV 里至少有一行 keep 或 discard。

## 调参：要训练或调参的组，每组都问用户

这组要训练或调参时，开组先问用户两件事：要不要自动调参；要的话，每方调几次。上一组问过，这一组也要再问。
只在开组时问一次：同一组里调完参、进入正式测试集评测时，不再问。用户开组时已经说了打算
（「不用调参」「每方调 10 次」），就算问过了，照着写进协议并注明日期，不再追问。
双方的调参次数必须相同，旧方案不能因为以前调过就少调或不调。

**只评测已冻结的方法（不训练、不调参）不问调参**，用 `evaluating-frozen-methods`，`调参` 写 `只评测，不调参`。
我们自己方法的新旧版本放在一起比，就得来自同一份训练条件，不是就按上文「旧方案也要重训」处理；
外部 baseline 可以用官方或复现的权重，见 `evaluating-frozen-methods`。

`调参` 这一行只能是下面四种写法之一：

| 写法 | 什么时候用 |
|---|---|
| `每方自动调参 20 次（用户 2026-09-23 确认）` | 用户给了次数 |
| `不调参（用户 2026-09-23 确认）` | 用户说不调参 |
| `沿用 main-result/mlp_gate 的每方 30 次，未确认` | 无人值守，问不到人 |
| `只评测，不调参` | 这组只评测已冻结的方法，不训练也不调参，见 `evaluating-frozen-methods` |

沿用只能照抄记录里**最近一次**用户确认的那组的次数；那组确认的是不调参，就写 `沿用 <组> 的不调参，未确认`。
用了沿用，这组的结论里也要写明次数未经用户确认。记录里从来没有用户确认过的次数，这组对比就不开跑：
把要问的问题写进 README 的待办，先去做别的。

调参怎么做、怎么记：

- 在验证集上挑配置，不在正式测试集上挑。只有挑出来的那个配置，在正式测试集上完整评一次。
- 一方的整轮调参在 CSV 里只记一行，`简介` 写调了几次、搜索范围。每次尝试的配置和验证集结果写进
  这一方输出目录里的调参日志。调参中途被打断（机器被抢占、超时）时，读日志接着调：已经试过的不重跑，
  只补剩下的次数，总次数仍按协议。
- 对比组不用 `running-experiments-on-branches` 的快速迭代模式：那套是每次尝试记一行、次数不固定，
  这里的次数就是协议里写的次数。
- 还想改方法本身（改代码、换结构），说明方法还没定型。回到探索组里迭代，定型后再开一组对比。

## 只认正式测试集跑满的结果

正式测试集通常在 `experiments/README.md` 里声明一次，写法和协议里那一行相同：写路径；只测其中一部分时
加 `N=数量`（只写正整数），不写 N 就是整个路径都要测。声明在哪一级 README，这一级下面的所有组都要跑它。
项目的历史记录里已经定好的测试集直接沿用，不自己另选。组里可以再加测试集，但不能替换上级声明的，
也不能改它的 `N`，包括给没写 N 的测试集加上 N。只评测的组例外，见 `evaluating-frozen-methods`。

`指标` 里用声明的路径标明每个正式测试集都跑满了：

- 声明写了 N：写成 `FID 12.3 @data/coco5k 1000/1000`（跑了 1000 个，要求 1000 个），脚本会核对数字。
- 没写 N：写成 `FID 12.3 @data/coco5k 全部`。脚本不核对数量，全靠如实标注：没跑完就不能写「全部」。

没跑满的结果这样处理：

- 小规模、smoke、在训练集上自测的数字，只能用来确认代码能跑：不写进 `指标`，不作为 keep 或 discard 的依据，
  也不报告给用户。
- 测试集没跑完记 `timeout`。crash 和 timeout 的 `指标` 都填 `—`，已经跑完的那部分结果留在日志里，
  不能当成全量结果报。

## 冻结后要改，先问用户

冻结后要改协议（换测试集、改训练条件、改调参次数），先问用户。改了以后，已经跑完的实验和新条件不可比，
另开一组。

## 收尾写 summary

- 正常收尾：每一方都在本组有 keep 或 discard 的记录，才能写 summary、下结论。
- 各方都没跑出正式测试集的结果（全部 crash 或 timeout）：summary 的 `指标` 填 `—`，结论写为什么
  没形成有效对比，不写谁胜出。
- 只要有一方跑出了正式结果，就按正常收尾处理：另一方也要跑完才能写 summary。

## 脚本会检查什么

| 什么时候 | 拦下什么 |
|---|---|
| `exp-plan`、`exp-finish` 写入时 | 协议缺字段或写法不对；`简介` 不以对照方的名字开头；keep 或 discard 的指标没有全量标注；crash 或 timeout 的指标写了数字 |
| 手写 summary 之后，用 `exp-check` 查组目录或 CSV | 一方已有结果、另一方还没有，就写了 summary（报错）；各方完成的次数不同（警告） |

这些检查由 `recording-experiment-results` 的 `scripts/memory.py` 执行，只对组 README 里有 `## 对照协议` 的组生效。

检查只看格式，看不出你是不是真的这样跑了。不要为了通过检查去补标注。

## 常见的偷懒想法

| 想法 | 实际 |
|---|---|
| 「旧方案已经有权重了，直接测省时间」 | 训练条件不同的两个数不能相减。重训 |
| 「旧方案以前调好了，这次只调新的」 | 调参次数不对等，新方案赢了也说明不了什么。同等次数 |
| 「测试集太大，先报个小规模的结果」 | 小规模的数字只证明代码能跑，不进记录，也不进报告 |
| 「上次问过调参次数了」 | 每组都问。只有无人值守时才沿用，并标明未确认 |
| 「只是评测，拿旧版本现成的权重直接测」 | 自己方法的新旧版本要来自同一份训练条件，不是就重训；外部 baseline 可以用官方或复现的权重 |
