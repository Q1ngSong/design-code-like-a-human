# 动手之前

两个目标：减少阅读负担，并控制本次改动的规模。为了避开旧代码而新增函数或包装层，
可能把同一项功能拆散，反而增加阅读和维护成本。

删除科研代码中的逻辑时，需要确认它是否影响实验结果。看似多余的 `clamp`、`+1e-8`，
或看似没有调用的分支，可能是复现原有结果所需的处理。删掉后，程序可能仍能运行，
但论文中的数值已经改变。


## 先把情况看清楚

动手前弄清楚这几件事：

- **谁会用它。** 找出已有调用方；如果它本身是 CLI 子命令、实验脚本或外部调度任务，
  写明如何触发。根据这些调用和入口确认当前用途。
- 输入从哪来、输出被谁消费、错误往哪传
- 现有实现和已装依赖里有没有能用的

对于启用了索引规范的项目（也就是说根目录有 `.comment-standard.json`），先刷新一次（第一次会自动建索引），再查：

    python3 ../../scripts/refresh.py <项目根> --base HEAD    先跑这个;项目没进 git 或还没有 commit 就去掉 --base
    codegraph explore <关键词>     相关符号的源码 + 调用链 + 波及面，一次拿到
    codegraph query <名字或说法>   按名字或注释内容搜，看看是不是已经有了
    codegraph callers <函数名>     谁在调它
    codegraph impact  <函数名>     改它会影响什么

`scripts/refresh.py` 位于插件根目录。上面的 `../../scripts/refresh.py` 以本技能目录为基准；
用调用时提供的技能基准目录解析为绝对路径后运行，不要相对于当前工作目录解析。

**刷新不能省，也不能用 `codegraph sync` 代替。** codegraph 不提取 Python 函数体内的
docstring，需要审计命令在 sync 后将其回填到索引。跳过回填，`query` 就无法按这些注释
检索，可能因此漏掉已有实现。

`sync` 按变动文件重建索引记录，会清除该文件所有函数的回填注释，包括未修改的函数。
因此每次修改代码后都要重新刷新，不能只在首次运行时刷新。

对于没启用规范的项目，使用 `grep -rn` 和直接读文件，慢一点，但这一步不能跳。

**「现有实现里有没有能用的」必须真去搜，不能靠印象。** 这条最常被跳过，
也最容易造出重复实现：项目里明明有个 `_normalize`，又写了一个
`normalize_maps`，两个都在，谁也不敢删。

codegraph 的全文检索将连续汉字视为一个整体，只能从这段文字的开头匹配。例如，搜索
`归一化` 无法匹配「把权重聚合并归一化到」中间的这三个字。**优先用英文术语搜索**，
英文单词通常由空格分隔；也可以换几个说法再查。

修改已有代码前，还要检查依赖它的位置。`codegraph explore` 的 `Blast radius`（波及面）
列出相关调用方，以及沿调用关系若干步内可到达的测试文件。**结果不保证完整**：跨文件的
动态调用、依赖注入和 `import X as Y` 别名都可能遗漏。将这些结果作为查找线索，修改
关键路径前，再检索函数名检查调用方。列出某个测试文件，只表示调用关系可达，不代表
测试覆盖了本次修改的分支。

不能仅凭调用方数量判断风险：一个调用方可能是对外接口，多个行为相似的内部调用反而
更容易调整。需要确认的是**调用方依赖哪些行为**：返回值形状、异常、副作用和调用顺序。

## 先分清：复现完整度由谁定

四道闸门问的是该不该写、写多大，前提是这东西的复现完整度由你定。

引一篇论文的方法、照参考实现搬、用户点名要某个算法——完整度不由你定，**规格是它的
原始定义**：论文的算法描述、官方实现、用户给的说明。动手前照规格把组成列一遍
（损失项、调度、归一化、初始化、默认超参），然后让整件事过四道闸门，不要拿闸门去
裁它的组件。某个组件说不出用处，是还没读懂，回去读，不是「还不需要」。

要省略、替换或简化其中任何一项，先说再动手；快速迭代期没人可问，就写进 task 名和
CSV `简介`（「简化实现：缺 A、B」），并且这一轮的数字只说明这个简化版，不能当成
那个方法本身的结论。

## 第一道：该不该存在

**没有当前用途的东西不写。** 这是个闸门，不通过就到此为止，后面三道都不用问。

科研代码里最常见的多余，是为还没发生的实验提前铺路：留一个 `model_type`
分派、抽一个 scheduler 基类、加一个「以后可能要换」的配置项。等真的要换时，
需求往往和当初设想的不一样，那层抽象反而挡路。

说不出用处的，就是还不需要。照规格实现的除外，见上一节。

## 第二道：能不能改现有的

**改动大小按 diff 算，不按「碰没碰旧文件」算。** 给原函数加三行判断，
通常比新写一个二十行的变体小得多。

增加一个函数，就多一处需要阅读和维护的实现，它与原函数的行为还可能逐渐不一致。
增加包装层时，读者还需要同时理解包装层和被调用函数。

### 保留实验记录后，可以追溯修改

按 `recording-experiment-results` 保存实验记录，并保留对应的代码后，可以在出现问题时
定位到具体尝试，取回当时的代码和参数重跑。确认调用方依赖的行为后，可以直接修改
现有函数，无需仅为避免修改旧代码而另写一份实现。

### 什么时候才该新写

**老路径还要能跑。** 做对照实验时基线和新方法都得能跑，这时不能把老逻辑
改掉。共用得多就给原函数加一个参数分支，几乎不共用才分开写。

**新东西确实是另一件事。** 不是原来那件的变体，只是恰好在附近。硬塞进原函数
会让它有两个不相干的职责。

**改原地会波及一堆本不需要变的调用方。** 比如为了一个新场景改掉返回值形状，
其余十个调用方都得跟着改。这时加参数或加一个薄包装更划算。

**改动会破坏现有测试。** 已有测试覆盖了旧行为，改动后需要大量重写测试。
这时单独写一个新函数，保持旧测试不变，只为新函数补测试。

除此之外，倾向于改原地。

## 第三道：新写的话，代码从哪来

按顺序看，能满足就用它，不再往下：

1. **代码库里已有的。** 用之前确认语义真的一致——名字像不代表行为一样，
   边界处理尤其容易不同。如果现有实现耦合了不相关的东西，复制一小段比
   强行复用更干净。
2. **标准库。** 例外是标准库方案明显更绕，比如为了套一个通用接口写出三层适配。
3. **已装依赖。** 不必为一个小功能引新包。但要确认这个包适合当前这条执行路径：
   只在测试里用过的包，不要直接放进训练主循环。
4. 都没有，自己写。

## 第四道：写成什么样

**最小可行实现应满足已确认的用途，并且不改变其他调用方依赖的行为。**
空实现、「能跑不报错」、按规格实现但缺少组件的简化版，都不算。在这个前提之上：

- 不加没有调用点的参数、分支、配置项
- 不为单一实现抽接口或基类
- 一个清楚的表达式能写完的，不抽成函数

反过来，如果压缩之后需要读两遍才懂，或者把错误处理藏进了链式调用，
就保持展开。行数少不是目标，能看懂才是。

## 目录结构缺失时

多数时候项目已经有结构，改动落在现有文件里，规划时说一句「改 `ovam/attention.py`，探针放
`temp_scripts/`，输出存 `runs/...`」就够；输出路径画不画树都按 `saving-experiment-outputs` 说定。
新项目、要加的东西没有落脚处、或平铺到分不清核心和脚本时，先调 `designing-project-layout`
拟一份目录结构，拿到树再走四道。`[一次性]` 的探针不进核心层，放最外层或层外。

**写出来的每个函数都要有 docstring，特殊方法（`__init__` 这类）除外。**
格式、角色标记、`Args` 里该写什么、哪一层可以少写，见 `writing-python-comments`——
那份是查询用的，写的时候翻一下。
项目根没有 `.comment-standard.json` 的，按项目自身惯例写。

## 不要为了简洁删掉的东西

以下几类看起来像多余的防御，实际不是：

- **随机种子的设置与记录。** 删掉之后结果不可复现，而这通常要到复现失败时
  才发现。

- **train / test 边界的隔离。** 简化掉就是数据泄漏。它不报错，指标还会变好看，
  是最难自查的一类错误。

- **数值稳定性处理**，如 `eps`、`clamp`、`nan_to_num`。它们经常没有注释，看着
  像随手加的，但去掉之后数值会悄悄偏移。真要动，先固定随机种子、用同一批
  输入跑一遍，对比论文里用到的那几个指标。

- **防数据丢失的错误处理。** checkpoint 写入失败要抛出，不要吞——调用方需要据此
  中止训练，否则会在无效状态下继续跑。

- **信任边界上的输入校验**：命令行参数、配置文件、外部数据文件。

- **用户明确要求的功能**，即使你认为它不必要。

R1 只能列出审计范围内未找到调用方的函数，不能直接作为删除依据。删除前还要确认它
不是入口或对外接口，也没有通过动态调用或别名使用；具体偏差见 `auditing-code-comments`。

清单之外的兜底、`try/except` 和参数校验，先查清楚它防的是什么：翻一下 git 记录，
或者看调用方会不会传出那种输入。查清楚了再决定删还是留。**实在查不清就留着，
并就近写一行注释说明「不确定这个分支是否仍然需要」**——分支本身没有 docstring，
注释写在它上面；整个函数存疑的才写进 docstring。留一个待办，
好过留一段没人敢碰的代码。

## 改了既有函数，记一行

如果改动影响了调用方能依赖的东西——返回值、异常、副作用、性能量级——
在 docstring 里加一行：

    变更: YYYY-MM-DD 未知名称改为直接报错，原兜底返回 ddim 的分支已移除。

重点写**原来那条路还在不在**。读代码的人多半不是来看你加了什么，
而是来确认他依赖的东西有没有动。

**只记录影响调用方的改动。** 重命名局部变量、提取私有辅助函数、改写等价条件表达式等
内部重构，无需记入 docstring，以免积累与当前行为无关的历史。

调整循环顺序不一定属于内部重构：它可能改变副作用或输出的顺序、异常抛出的时机，
以及浮点累加结果。不确定时，按调用方能够感知的改动处理。
新增函数仍需写 docstring 描述当前行为，但不写 `变更:` 行。

快速迭代期间不为每次尝试逐条补 `变更:` 行；合并前对照主分支，统一说明最终保留的行为变化。

**审计规则 C1 会检查这一项**，但它只是兜底机制：对比 `HEAD`（带 `--base` 时是那个 ref）找出签名或函数体变了、
`变更:` 却没增加的函数。它数的是次数，判断不了内容——「第二道」里加参数那种
改动它会报，但报了不等于你写对了，写一行没信息量的也能通过检查。
所以不要依赖工具判断，该写的时候就写清楚。

规则的完整行为与处置见 `auditing-code-comments`。

## 要改的地方太多时

如果发现加一个功能得改五六处，先停下来问一句再动手。

横切功能、协议实现、数据迁移本来就可能涉及多处修改；也可能是现有接口不适合当前需求，
需要先调整结构。仅凭修改数量无法区分，即使接口划分不合理，每一处修改也可能看似必要。
**把需要修改的位置列给用户**，由用户判断按计划修改还是先调整结构，不要自行决定重构。

**这条只在构建期。** 快速迭代期（见 `running-experiments-on-branches`）没人可问，
自己定——但四道闸门一道不少：该不该存在、能不能改现有的、代码从哪来、
写成什么样。判断标准一致：五六处改动是同一个想法的自然延伸就做；
是在绕一个不合适的接口就不做，换个想法试。快速迭代里改错了 stash 掉很便宜，
但一次尝试变成一次重构，跑出来的数字就说不清是想法有效还是结构变了。

## 做完给用户回复

代码先行。之后只说两件事：这次**没做**什么，以及什么条件下该补上。
做了什么代码本身已经写着，不用复述。照规格实现的，对着动手前列的那份组成
清单逐项说，别凭印象说都做了。

无人值守的判定见 `auditing-code-comments`。此时同样这两件事
写进这一轮的记录——`recording-experiment-results` 的 `结论` 列，或 commit
message——别丢。这时「先把情况看清楚」里那次刷新（带着 `--base HEAD`），只看
`changed=true` 的 finding 和 `unindexed_files`：存量告警每轮都一样，不用重读。
快速迭代里动手前工作区是干净的，`changed=true` 为空是正常的，不是漏了。
