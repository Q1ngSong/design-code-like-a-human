# 复现别人的代码

**论文里报告的数字不可信。** 它只有一个用途：判断我们自己跑出来的数对不对。
它不进实验记录，不进论文表格，不进任何对外结论。我们说出口的每个数字，都得是自己跑出来的。

**排查过程里跑出来的数字也不算数。** 随机权重跑的、只喂了一小批数据的、缩小规模试通路的，
这些数是用来确认代码通不通，不是结果。它们比论文数字更容易混进对照表，因为确实是我们自己跑的。
写进报告时就标死用途，别让它孤零零躺在某行日志里等人误读。

**判断要落盘。** 跑不通卡在哪、上游是哪个 commit、和论文差多少——这些结论只说在对话里，
这一轮结束就没了。`reference_proj/` 随时可以删掉重来，`BASELINES.md` 不行，
它是这件事唯一留得住的部分。

## 这篇论文在项目里是什么角色

| 角色 | 要求 |
|---|---|
| 作为 baseline | 必须跑起来。跑不起来就不能拿它做对照：换一个，或者在 `BASELINES.md` 写明这个对照缺位、少了它影响哪些结论 |
| 作为方法论参考 | 尽量跑起来。跑不起来交错误报告 |
| 仅作引用 | 尽量跑起来。跑不起来交错误报告 |
| 没有公开代码 | 不复现。`BASELINES.md` 里留一行说明它没有代码、不能用作对照，**不要记它的数字** |

角色由用户定。无人值守时按记录里已经写下的角色完成复现任务，不自己改判。

没有公开代码那一行是留给下一个人的：没有它，几个月后会有人再评估一遍同一篇论文，
再得出同一个结论。不记它的数字，是因为数字一旦落在这个文件里，旁边就是我们自己的数字。
两个数并排放着就会被读成差距，哪怕我们连它们是不是同一个指标、同一套划分都还不知道。

## 东西放哪

上游代码、运行日志、原始输出、错误报告全文，都在 `reference_proj/<baseline_name>/`，不入库。
**复现在那个目录里完成，不动我们自己的代码。** 根目录的 `BASELINES.md` 入库，每个 baseline 一节：

    ## <baseline_name>
    - 来源: <URL> @ <commit>
    - 论文: <标题或 arXiv id>；目标数字出处: <表 X / 第 Y 节 / 哪个设定>
    - 角色: baseline | 方法参考 | 仅引用
    - 状态: 未开始 | 通过 | 未通过 | 未复现
    - 我们的数字: <指标=值>（设定: …）
    - 论文的数字: <指标=值>   仅用于本次判定，禁止引用
    - 环境: Python <版本> / <主框架>=<版本> / CUDA <版本> / 激活代码(conda activate <env> 或 source <env>/bin/activate)
    - 差距与判定: <一句话，含具体差距>
    - 中间文件: reference_proj/<baseline_name>/

`reference_proj/` 不入库，所以 commit、判定、差距这几样必须写进 `BASELINES.md`。
中间文件丢了可以重跑，这几样丢了找不回来。

复现本身只产生一处入库改动：`BASELINES.md`。不需要为它开实验分支，
也不在 `experiments/` 下建 CSV——那里的每一行是我们自己跑的一次尝试，复现不是。

**把这个 baseline 接进我们的实验去收集数据，是另一件事。** 那些脚本写在我们自己的代码目录下
（`temp_scripts/<baseline_name>/` 之类），入库，按最外层的规矩写 docstring 和角色标记。
它属于实验阶段：按 `running-experiments-on-branches` 开分支，按
`recording-experiment-results` 记录，`experiments/` 里那一行记的是那次数据收集。
一篇论文需要的那几个 baseline 通常算一组，一起开一个分支。

## 跑之前先登记

克隆下来第一件事是记身份：

    git -C reference_proj/<baseline_name> rev-parse --short HEAD

连同来源 URL 写进 `BASELINES.md`。不记 commit，几个月后没人说得清当时跑的是哪一版，
上游改过什么也对不上。

同时写下目标数字和它的出处，具体到哪张表、哪个设定。出处写不出来，说明论文还没读清楚，
回去读，不要凭印象填一个数。

## 算不算复现成功

没有统一的容差，差多少算过由你判断。判断要留下依据：

- **写出实际差距**：我们的数、论文的数、同一个指标同一个设定。说不出差距就不下判定。
- 判定写成这几种之一：
  - **通过** —— 跑起来了，差距可接受，理由已经写下。
  - **未通过** —— 跑起来了，但差距过大，或者说不清差在哪。
  - **未复现** —— 跑不起来，交错误报告。
- 登记了目标数字却没有判定，等于这次没收尾。

两个数不可比就先说清楚再比。测试集对开发集、不同的数据划分、不同的评测协议，
数字本身再准也不能相减。对不上的地方写进那一节，不要为了凑出一个差值就假装口径一致。

**改了预处理、数据划分或超参，基线和我们自己的方法要一起改**，并写明改了什么。
只改一边不会报错，指标还会变好看，是最难自查的一类结论污染。

## 跑不起来的时候

写一份错误报告，放 `reference_proj/<baseline_name>/`：

    ## 卡在哪一步
    ## 错误原文        原样贴，不要转述
    ## 试过哪些修法
    ## 判定与建议

`BASELINES.md` 里留一两句结论和这份报告的路径。

排查过程中确认过的事实一并写进报告，哪怕它不是失败原因。模型能不能构图、参数量多少、
依赖实际装的是哪个版本——下一个人接手时，这些省掉的是重复劳动。

修的预算是固定的：同一个错误最多修两次。两次不通就换一条路——换版本、换安装方式、
换入口脚本——最多再两次。还不行就写报告收场，并说明卡住的是环境、数据，还是上游代码本身。
第一次失败就放弃不行，无限试也不行。

## 无人值守时不要停下来问

拿不到的东西写成待办留在那一节里，能确定的部分照常填完。论文标题对不上、评测协议不清楚、
数据集要人去下载——这些写下来，本身就是这一轮的产出，人回来一眼看到卡在哪。
停在对话里等回答，这一夜就白跑了。

`BASELINES.md` 的改动照项目习惯提交，不要留在未跟踪状态等人来收。

## 复现通过之后

复现只负责证明这份代码在我们手上能跑。要进论文对比表的那次运行，按实验组重新跑一遍，
和我们自己的方法用同一套设定、同一套记录，见 `running-experiments-on-branches` 和
`recording-experiment-results`。`BASELINES.md` 里的数字属于复现阶段，不直接搬进论文。

照论文自己重新实现一份，而不是跑别人的代码，那是 `writing-minimal-code` 里
「复现完整度由规格定」那一节的事。
