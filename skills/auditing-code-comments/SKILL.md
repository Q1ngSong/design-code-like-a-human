# 审计注释、边角料与分层

用在**功能已经跑通之后**。功能没通就先去把功能弄通 —— 对着不工作的代码
做审计是浪费。例外是快速迭代的**跑前审计**（`running-experiments-on-branches`）：
`--base HEAD` 只看这次改动上的告警，为的是在烧 GPU 之前抓到 D3 这类错。

## 前提

项目根需有 `.comment-standard.json`。没有则该项目未启用——
**先问用户要不要启用，不要自作主张创建。**

这个文件里的每一项都是用户的声明，不是你的判断：

| 键 | 声明的是 | 影响 |
|---|---|---|
| `layers` | 哪些目录构成依赖层，由核心到外围；一层可以有多个平级目录，写成列表 | 不写则 R2 跳过；D1 只要声明了 `vendored` 也会跑 |
| `vendored` | 哪些目录是复制进来的第三方代码 | 不写则那些代码会被当自己的审 |
| `output_roots` | 实验输出根目录的名称，写成列表，即使只有一个也写成 `["runs"]`；更换目录后，新旧名称都要包含，如 `["runs", "runs-v2"]` | 默认 `["runs"]` |
| `codegraph` | 索引范围的加减 | 见 `references/setup.md` |

最小配置是 `{}`。不声明层级时，R2、D1 跳过；其他规则按各自前提执行，例如
R1、R3 需要索引，C1 需要 Git。默认输出区 `runs/` 存在时，D2 也会检查它。

**你不改这个文件。** 审计时发现该声明而没声明的，在汇报里说明理由和建议写法，
由用户决定。两种最常见的：

- 项目明显有分层结构（核心包、脚本目录、临时脚本），但没写 `layers`——
  建议写上，能启用 R2 和 D1
- 有复制进来的官方代码（如 `sd15/`），但没写 `vendored`——那些函数会被大量
  报 R0，而它们本来就不该按我们的标准写注释

配置 `layers`、补充 `.gitignore`、确认索引范围或检查误入库文件时，参见 `references/setup.md`。

## 无人值守

无人值守标记是 `.codegraph/unattended`：文件存在且距修改时间不足 24 小时时有效。
`audit.json` 的 `unattended` 字段和会话开头的 hook 提示只是读取时的快照；若状态可能
过时，检查标记是否仍存在及其修改时间，不能只用 `cat` 读取文件内容。设置和清除方法见
`running-experiments-on-branches`。用户已明确停止时，按停止步骤清除标记。

本技能中需要用户判断的事项，在无人值守时这样处理：

- **不问。** 没人可问，问了就是卡住。
- **不改。** 不建 `.comment-standard.json`、不动 `codegraph` 配置、不删文件、
  不拿存量 finding 去改代码。落在这次尝试上的告警（`changed=true`）归驱动层的
  规矩管——README 的例子里 D3 改掉再跑、R1 删掉。审计的产出本来就是提案不是补丁，
  无人值守只是把「等确认」改成「不确认就不动」。
- **不拦。** 退出码 1 不是停下的理由。findings 在 `audit.json` 里，
  驱动层（你的 `program.md`、ARIS 的循环）决定处理哪几条、忽略哪几条。
- **记录自行决定的事项及理由。** 原本需要询问用户、但按无人值守规则可自行决定的事项，
  把选择和理由写进 commit message 或 CSV 的简介/结论列。
- **保留需要用户决定的事项。** 是否启用规范、如何声明 `layers`、R3 如何处理、
  误入库文件是否移出，都留待用户决定。当前报告能反映的事项随报告提供；未启用规范等
  导致无法生成报告的事项，写入本轮记录。不要把重新运行审计当成已记录这些事项。

两条底线不因无人值守放松：

- **退出码 2 不是 finding，是审计本身没跑成**（配置损坏、`--base` 的 ref
  不存在）。写进这一轮的记录，实验循环照常——但别把它当成「审计通过」。
  连续几轮都是 2 就不再调审计，每轮记一句「审计不可用」，**实验照跑**——
  停的是审计不是循环。人回来看到那一串就知道环境有问题。
- **「不要为了简洁删掉的东西」那张清单**（`writing-minimal-code`）无人值守时
  反而更硬：有人在场删错了当场能问，没人在场删错了要到复现失败才发现。

有人在场时照旧：一条一条过，得到确认再动。

## 运行

    python3 ../../scripts/refresh.py <项目根> --json


**差异审阅加 `--base <ref>`**:审计仍是全仓库的,但报告会把落在改动上的告警——
改了签名、体或 docstring 的函数、新文件(含还没 `git add` 的)、改动文件里的模块级语句——
单独列成「本次改动」一段,放在「存量」前面。抓不到的是图效应:删了调用点让
别处没动的函数新报 R1,那种落在「存量」里。ref 怎么给:

| 场景 | ref | 为什么 |
|---|---|---|
| 快速迭代,跑前审计 | `HEAD` | 这次尝试还没 commit,工作区里就是它的改动 |
| 合并前检查 | `main` | 整条实验分支相对主分支的改动;C1 也比 main,整条分支改了没记的都报 |
| 有人在场,想看某两个分支之间 | 人指定,如 `--base develop` | 用户自己说比什么 |
| 省略 | —— | 全仓库审阅,不分段;C1 仍比工作区 vs HEAD |

ref 不存在时退出码 2,`error` 字段说明。
`scripts/refresh.py` 位于插件根目录。上面的 `../../scripts/refresh.py` 以本技能目录为基准；
用调用时提供的技能基准目录解析为绝对路径后运行，不要相对于当前工作目录解析。

命令依次写出 codegraph 配置、建立或更新索引、将 Python 函数体内的 docstring 回填到索引，
最后执行规则检查。**首次运行会自动建立索引**，等待索引建立完成后再检查，因此正常情况下
同一次运行就能得到图规则（R1/R2/R3/D1）的结果。若提示「未找到索引」，查看 `sync` 中的
失败原因，如 codegraph 未安装、超时或执行报错，处理后再运行。

**不要单独运行 `codegraph sync`。** sync 会把变动文件在索引里的记录整个删掉重建，
清空回填结果，注释会从索引里静默消失。

`--json` 每个字段的含义见 `references/handling.md`。

### 报告文件

检查完成并返回退出码 0 或 1 时，在项目的 `.codegraph/` 下**覆盖写入** `audit.md`（供人阅读）和 `audit.json`
（与 `--json` 的标准输出相同）。报告仅反映本次运行，不保留历史，也不与上次结果比较。
退出码 2 表示审计未能执行，不生成新报告；磁盘上已有的报告不能当成本次结果。

没有索引时也会覆盖报告，但标题和正文开头会标明「结果不完整」，概览表将 R1/R2/R3/D1
列为「未执行」。此时告警条数减少可能只是因为这些规则未执行，不能据此判断问题减少。
向用户汇报时附上 `audit.md` 的路径。

## 规则

| 规则 | 判定 | 通常怎么处理 |
|---|---|---|
| R0 | 缺 docstring 或角色标记 | 补上，一行也算合格 |
| R1 | 审计范围内找不到调用它的地方 | **入口函数会被报**，先确认是不是对外接口；私有函数则大概率是死代码 |
| R2 | `[一次性]` 不在最外层 | 移到最外层目录，不是删除 |
| R3 | 主线调用了旁支 | **需要判断**，见 `references/handling.md` |
| R4 | `def` 那一行有的参数，Args 里没写 | 补 Args 条目 |
| R5 | 有返回值或 `yield`，但没有 `Returns:` / `Yields:` | 补上 |
| R6 | Args 里写了 `def` 那一行没有的参数 | 改参数时漏改了文档，同步过来 |
| D1 | 内层引用外层 | **模块化崩坏的信号**，见 `references/handling.md` |
| D2 | 输出区目录存在但未被 `.gitignore` 忽略 | 建议用户在`.gitignore`加一行 `runs*/` |
| D3 | 写盘点写死了输出路径 | 在脚本入口定一次 `out`，写盘改成 `out / "文件名"` |
| C1 | 改了已有函数却没加 `变更:` 行 | **需要判断**，见 `references/handling.md` |

判断告警是否合理、是否存在漏报，或了解规则的执行条件和已知偏差时，参见
`references/handling.md`；其中也说明了 R3、D1、C1 的具体判断方法。

## 绝不自动修改

**审计的产出是提案，不是补丁。** 逐条和用户过，得到确认才改。

某些看似多余的逻辑会影响实验结果。删除后，即使程序没有报错，论文中的数值也可能改变。
具体例子见 `writing-minimal-code` 开头的说明。

所以：

- **不要批量修**，一条一条来
- **动之前先说清楚**这段代码可能在做什么、删了会影响哪个结果
- **拿不准就不动**，标记出来让用户判断
- **凡是碰到会进论文的数值路径，先跑一遍确认结果没变**

## 汇报

按规则分组汇报，R3、D1、C1 单独列出并附判断依据。每条说明是否建议修改、原因和具体改法。

以下事项作为建议提出，由用户决定是否处理：

- 需要声明但尚未声明的 `layers`、`vendored`
- 索引中明显多余的目录，或建立索引明显变慢的情况
- 已入库但按当前 `.gitignore` 应忽略的文件

没有发现值得修改的内容就直接说明。机械 finding 提供问题位置，但不提供可删除代码的
行数，不要据此估算「可删约 N 行」。
