# 写 Python 注释

仅适用于根目录有 `.comment-standard.json` 的项目。没有这个文件说明该项目
没有启用本规范,按项目自身惯例写即可。

## 结构

    """<摘要:一句话,英文术语原文 + 中文说明>。[角色标记]      ← 必填

    <正文:功能是啥、为什么存在、与主线什么关系、有什么前提>    ← 可选

    Args:
        <名>: <形状/dtype/单位/取值范围> — <含义与约束>       ← 有参数则必填
    Returns:
        <类型/形状> — <含义、状态、所有权>                   ← 有返回值则必填

    变更: YYYY-MM-DD 改了什么,原路径是否受影响              ← 仅修改已有函数时
    """

书写量随函数接口自动伸缩:无参数无返回值的一行即合格,有参数就每个参数一条,
有返回值就写 Returns；生成器用 Yields 说明每次产出的值。私有函数也不豁免。

**例外是最外层。** 声明了两层以上时,`layers` 末项(可以是多个目录)里的函数
只要摘要行和角色标记,不要求 `Args`/`Returns`——没有内层依赖那一层,调用方只在
同层,读者就是写它的人,逐参数介绍对他没有信息量,审计规则 R4/R5/R6 也不查那里。
单层项目没有最外层,全部按最严的写。

**Python 特殊方法不用写。** 两端双下划线的方法——`__init__`、`__call__`、
`__len__` 这类——行为由语言规定，审计规则也跳过它们。给 `__init__` 写一遍
「Args: 构造参数」是重复信息。

最后那行 `变更:` 只在**改动已存在的函数、且改动影响到调用方能依赖的东西**时才加,
新写的函数不加。什么算「影响调用方」、多次修改怎么办、审计规则 C1 能查到什么,
见 `writing-minimal-code` 的「改了既有函数，记一行」一节；快速迭代期间的变更记录在合并前统一补齐。

## 摘要行

**技术术语保留英文原文,不翻译。** 写 `SDXL pipeline`、`UNet`、`scheduler`,
不写「稳定扩散超大模型管线」。codegraph 的 `explore` 对中文查询零命中,
英文术语是它唯一能抓住的锚点;中文说明留给 `query` 和人。

**关键词放在开头，或用标点与前文分开。** codegraph 的全文检索将连续汉字视为一个整体，
只能从这段文字的开头匹配。例如，搜索「归一化」无法匹配「把逐层权重聚合并归一化到 [0,1]」；
改成「归一化:把逐层权重聚合到 [0,1]」后即可匹配。

## 角色标记

| 标记 | 含义 | 后果 |
|---|---|---|
| `[主线]` | 本次实验的核心路径 | R3 会检查它有没有调用旁支 |
| `[旁支]` | 静态可达但不在主线上 | 审计时要回答「本次实验用得到吗」 |
| `[基础设施]` | logging / config / io 等底座 | 没有规则特殊对待它；没人调用照报 R1 |
| `[一次性]` | 探针、临时脚本 | 必须位于最外层;R1 不报它零调用者 |

## 正文

摘要装不下的才写:功能怎么走、为什么存在、与主线什么关系、有什么前提。

**不要把摘要换个说法重写一遍。** 摘要回答「做什么」,正文回答「怎么做、
为什么在这儿」。一句话说尽的就不写正文。

`[旁支]` 的正文不能省 —— 审计只能告诉你「主线调用了旁支」,该留该删要读正文
才能裁决。正文缺失时审计结论就退化成一份无从判断的清单。

## Args / Returns

**`def` 那一行已经写明的东西不要重复。** 参数名和类型注解读代码时就看得见,
`ckpt (str): checkpoint 路径` 等于把它抄了一遍,是噪声。有价值的是:张量形状、dtype、取值范围、是否已归一化、单位、
非法输入的处理方式、副作用与所有权、惰性求值这类使用约束。

不设 `Raises:` 字段。异常几乎总是某个参数取值约束的后果,写在对应的
`Args` 行里(「未知名称直接抛 KeyError」)。

## 写完之后

先核对注释是否准确描述当前行为，再运行审计检查格式和遗漏。R0/R4/R5/R6 会指出
缺角色标记、参数未介绍、缺 Returns/Yields、Args 中的参数名与函数签名不一致等问题；
规则通过不代表注释内容正确。

怎么跑、结果怎么读,见 `auditing-code-comments`。会话开始时 hook 也把
带绝对路径的完整命令打出来过,直接用那条最省事。
